# 小红帽：后传

[English](README.md) · **简体中文**

![Unreal Engine 5.3](https://img.shields.io/badge/Unreal%20Engine-5.3-313131)
![Solo graduation project, 2024](https://img.shields.io/badge/solo%20graduation%20project-2024-A4271C)

《小红帽：后传》（Little Red: Sequel）是一款用 Unreal Engine 5 制作的叙事向 RPG 游戏 Demo：2D 像素角色行走在手工搭建、使用像素贴图的 3D 场景里。你扮演新一代的小红帽。村子给她定了规矩：沿着大路走，永远穿红色，遵循童话书里的预言，也就是被大灰狼吃掉。游戏讲的是她不再照着书走之后发生的事。这一页介绍它是怎么做出来的：故事和分支、场景、资产流程，以及背后的几套系统。

AI 工具帮了忙，用在哪里这一页都写明了。像素贴图由 Stable Diffusion 生成，再由我在 Photoshop 里按每个模型的 UV 修整。ChatGPT 参与了部分 C++ 头文件的修改、一些蓝图逻辑和故事文本，生成的内容都由我手动修正后再整合进项目。AI 工具对单人开发者能有多大帮助，本身就是这篇毕业论文要探讨的问题之一。

这是我 2024 年的专科毕业设计（数字媒体技术专业，上海南湖数字创意系），一个人用大约三个月完成。它是一个可以游玩的 Demo，已实现部分计划中的剧情，不是完整的游戏。

本仓库只包含展示材料：项目介绍片、游戏演示视频、截图、制作过程图和展览海报。Unreal 工程文件不在其中。本项目随一篇中文毕业论文一同提交，论文题目是《数字媒体技术在游戏产业的创新应用：以独立游戏为例》（2024 年 5 月），没有在这里公开。

## 要解决的问题

一款叙事向 RPG 需要写好的故事、照计划搭出的场景、一大批美术资产，以及任务、对话、菜单和存档系统。这个项目想弄清楚，一个人在大约三个月里能把其中多少做完：

- 什么样的画面风格，能让一个人在制作效率和质量之间取得平衡？
- 一个有分支、有双视角的故事，怎样在写任何对话之前就规划好？
- AI 工具能在策划、程序和贴图上补哪些短板，哪些仍然要靠人检查？
- 原本并不配套的现成插件，能不能整合成一个游戏？
- 需求分析、排期、版本管理和技术预研这些工业化做法，团队只有一个人时还管不管用？

游戏给出的回答是：2D 加 3D 的画面风格、先于文本画好的故事流程图、AI 辅助的贴图流程，以及用我自己写的蓝图串起来的三个修改过的商城产品。

|---|---|

| 1. 俯视概念图，标出主要资产的位置 | 2. 同一座岛的白盒和打光后的场景 |

1. **概念图。** 用 Inkarnate 画俯视地图，确定主要建筑和地标的位置。
2. **白盒。** 在 Unreal 里摆放大型结构（房屋、塔楼、桥），其余中小型资产先用方块代替。
3. **地形。** 用一个带摄像机的蓝图固定玩家的俯视角度，在这个视角下按概念图刷地形高度，再用图层混合材质刷出岩石、泥土、草地和石子路。
4. **材质。** 用 xNormal 从颜色贴图生成法线贴图。在 Unreal 里给每个资产建材质实例，可以调法线强度、UV、金属度、粗糙度和高光。
5. **打光。** 加入灯光、特效、后处理体积、指数高度雾和天光，对照打光后的画面调整材质实例，最后烘焙光照。每个室内场景都走一遍同样的流程。

| 特效 | 用 Niagara 制作的火焰、萤火虫和烟雾；自发光的灯和火；用 After Effects 和 Houdini 制作的启动 Logo 和粒子动画 |
| 资产 | 约 199 套美术资产：3D 约 124 套，2D 约 75 套，另有特效、后处理和角色动画 |

## 设计原则

- **熟悉的故事，被质疑的角色。** 在这个世界里，每个人出生时都带着一本童话书。大多数人的书是空白的；少数人是"主角"，他们的书里早已写好了一生，要做的就是照着演完，好让自己的故事被抄进每个人的童话书里，用来教育后人。童话书里的主角永远正义勇敢，现实却未必：有的"主角"并非如此，有的"反派"也不是自己选择作恶。小红帽是少数拒绝照着剧本走的人之一。这个世界本身是由人工智能创造的，而生活在其中的人并不知道。
- **双视角。** 第零章结束后，玩家可以继续扮演小红帽，也可以切换到大灰狼的视角，他开始怀疑童话书里描写的那个怪物般的自己。两条故事线会交叠，并走向同一个目标，同样的事件可以从两边各看一遍。
- **分支取决于玩家做过什么。** 章节按条件解锁。比如前期，小红帽在被村长施压之前有没有和旅行商人交谈、隐藏数值是否大于零，决定了她走向一个坏结局，还是继续前往狼人村的那条线。更一般地说，隐藏数值超过阈值后，会开启不同的故事线或结局。
- **先画图，再写文本。** 我先写了多套完整的故事方案（概述、主线、主题和参考），从中选定一套；再把整个故事画成流程图，包含两条角色线、各章节名称、解锁条件和每章摘要，然后据此编写对话和任务。
- **含蓄的引导。** 游戏前期不直接指向真相，而是让玩家自己发现村民所说的和眼前所见之间的落差。部分段落会打破第四面墙，直接与玩家对话。
- **一个人做得出来的风格。** 2D 像素角色加上使用像素贴图的 3D 场景，观感接近 HD-2D 游戏。我调研了几款把两者结合起来的独立游戏之后选定了这个风格，因为对单人开发来说，它在制作效率和质量之间比较平衡。

**设计之前的调研。** 我分析了十款来自 Ludum Dare、itch.io、Reddit GameJam 和 Global Game Jam 的作品，每款都记录了制作背景、作品分析和可以借鉴的想法；叙事和 Meta 方面的点子，以及把交互做小做精的思路，都来自这里。之后我更深入地分析了十款上过 Steam 独立游戏排行榜的作品，"2D 像素加 3D"的风格、非线性叙事、多结局和双视角，都先对照这些已经上线的游戏验证过。我还整理了一张游戏制作中 AI 技术应用的表，并调研了一款商业游戏是怎么使用 AI 功能的。

**资产。** 用一张表跟踪所有资产：中英文名称、优先级、进度、所属场景、截图、白盒设计和参考图。3D 资产先在 Maya 里做白模，用 RizomUV 展 UV，再用 Stable Diffusion 生成像素风贴图（融合两个像素风 LoRA，搭配像素风 SDXL 底模，图生图），然后在 Photoshop 里按 UV 修图。按这套流程，每天能完成十个左右的资产。道具、角色和动画在 Aseprite 里绘制，其中角色像素图是对照参考图画的。

**程序。** 大部分玩法逻辑用蓝图实现。任务系统、对话系统和主菜单分别来自三个不同的虚幻商城产品：一个任务插件（C++ 类配合节点式任务编辑器，支持多种任务类型、完成条件判定和屏幕上的任务追踪）、一个带节点式分支对话编辑器的对话插件，以及一个菜单资产（新游戏、继续游戏、读档，以及调用 Unreal 设置 API 的图形和声音设置，界面用 UMG 制作）。它们原本并不配套，所以程序上很大一部分工作是修改它们，并把它们整合进同一个游戏。任务是我在任务插件的编辑器里编写的。玩家蓝图和交互蓝图是我自己写的。

## 出过的问题怎样变成规则

| 遇到的问题 | 改了什么 |
|---|---|
| 生成的贴图不能无缝衔接，我也没找到稳定的解决办法 | 这套贴图流程只用于像素风格，像素美术不容易看出接缝 |
| 任务、对话和菜单这三个商城产品原本并不配套 | 每一套都先修改，并在小的测试工程里试过，再整合进游戏 |
| 筹备阶段有些资产没达到可用标准 | 在第二阶段重做，并提前多做一批备用资产，这样某一批没通过检查时不会拖住进度 |
| AI 生成的代码和故事文本拿来不能直接用 | 每一处结果都由我手动修正后再整合 |
| 几项任务争抢同一段时间 | 策划文档优先于程序，程序优先于美术 |

## 怎么检查的

- 每个资产都放到 Blender 的 Cycles 渲染器里预览，合格后按规范命名，截图登记到表里。
- 每种方法都先测试再采用：包括贴图流程（其中试过用 ComfyUI 工作流替代 WebUI），以及菜单、任务和对话系统，每一套都先在一个小的测试工程里做出来、试过，再搬进游戏。
- 每周对照计划统计各项任务的耗时并做调整。

## 还没做完的

- 这是一个 Demo，只有部分剧情可以游玩，一些计划中的功能因为时间不够被删减了。
- 菜单为中文，剧情文本只有英文，语言切换功能没有做完。
- UI 美术比较基础，部分界面和音频是占位内容。
- 已知问题：读档时偶尔会卡在加载界面。

## 这个项目说明了什么

- 这是我第一次把一款游戏从空白文档做到打包成品，也让我看清了制作各环节之间是怎么互相牵制的。
- 工业化流程缩小到一个人同样有用：需求分析、排期、版本管理和技术预研，对单人项目和对团队一样管用。
- AI 工具补上了我在策划和程序上的一部分短板，也加快了贴图制作，但生成的内容仍然需要自己检查和修改。
- 我有意减少了传统美术的比重，把时间更多放在技术美术和程序上。这也是我后来升本选择软件工程的原因。

## 哪些做法可以用到仿真和可视化上

这是一款童话游戏，但其中有几部分工作，和搭建仿真或可视化场景时要做的是同一类事情：

- **照着地图搭出一个地方。** 先有地图，再做白盒，再按地图雕刻地形，最后做成成品场景。把参照物换成海图或总平面图，工作顺序是一样的。
- **光照和氛围决定能看见什么。** 烘焙光照、天光、指数高度雾、体积光和后处理体积，决定了玩家能看多远、什么最显眼，夜晚的室外和点灯的室内都是这样处理的。
- **材质做成可复用的。** 一套图层混合的地形材质，每个资产一个带可调参数的材质实例，还有随风摆动的植被。
- **有记录可查的资产流程。** 约 199 套资产走的是同一套步骤：命名规范、跟踪表，进引擎之前先渲染检查。
- **性能设置交给使用者。** 设置界面通过 Unreal 的设置接口开放了分辨率、窗口模式、帧率和画质预设。
- **让各自独立的系统合成一个。** 两个 C++ 插件和一个菜单资产原本并不配套，经过修改后接到了一起，每一套都先在小工程里单独验证。
